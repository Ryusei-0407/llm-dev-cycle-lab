# dev-cycle: 実装とテストを並列で進める機能開発サイクル

「E2Eは最後にまとめて」を禁止し、機能単位でE2Eまで完了させる。
テスト層の判定表と共通規約は docs/POLICY.md(このスキルでは繰り返さない)。

## Phase 0: 仕様化(メインセッション)

`specs/<feature>.md` を書く: ユーザーストーリー、受け入れ条件、公開インターフェース
(APIエンドポイント、型、data-testid)、テスト観点の層割り当て。

test-writer は仕様**だけ**からテストを書くので、仕様には検証に必要な具体物
(ワイヤフォーマット、実データ例、モックの型)を含める。散文より具体物が効く。
仕様が曖昧なまま先へ進まない — テスト観点を仕様に含めることが後段の暴走を防ぐ。

## Phase 1: 並列実行

test-writer と implementer を**同一メッセージで同時に起動**する(各自 worktree 隔離)。
どちらにも `specs/<feature>.md` を渡す。worktree 毎に `WEB_PORT`/`API_PORT` を別値で
割り当てる(例: 6180/9780、6280/9880、6380/9980、… — 本体の既定 5173/8787 と重ねない)。

厳密なTDDが必要な複雑な機能では直列版に切り替える:
test-writer を先に完了させ、失敗テストをコミットしてから implementer を起動する。

## Phase 2: マージと検証

テスト → 実装の順にマージし、ユニット → その機能のE2E の順でグリーンにする
(TDDゲート併用: `touch .claude/tdd-gate`)。
implementer がテスト側の問題を指摘していた場合はここでメインセッションが裁定する。

**この機能のモックE2Eがグリーンになるまで、機能は「完了」ではない。**

## Phase 2.5: 反証(敵対的レビュー)

adversarial-reviewer を新規コンテキストで起動する。渡すのは仕様と機能名のみ
(実装経緯・会話コンテキストは渡さない)。

- 反証が成立したら: **反例をテストとして固定(そのテストがミューテーションを殺すことを確認)
  してから**修正に入る。反証はテスト資産に変換する
- 幾何・データ量・環境要因の反例は、`page.route` の固定データで前提条件ごと
  決定的に再現する(POLICY 共通規約のモックレーン)。共有DBに前提データを
  積む固定方法は、他テストの幾何を変えて波及する
- 反証失敗(頑健)なら: そのまま Phase 3 へ。空振りは正常な結果
- 再現手順のない指摘・correctness に関係ない指摘は対応不要(過剰報告はレビュー側の失敗)

## Phase 2.6: 中断・破壊操作レビュー(非同期面を持つ機能のみ)

ミューテーション・ストリーム・複数ステップ UI・楽観 UI のいずれかを持つ機能では、
disruption-reviewer を新規コンテキストで起動する(渡すのは仕様と機能名のみ)。
送信中リロード・タブ閉じ・二重クリック・オフライン・セッション失効などの
中断ベクタを実行し、**サーバ状態まで**観測して報告させる。

- 反例(データ二重・消失・恒久スタック)が成立したら: 修正の前に反例を
  `@disruption` タグのテストとして固定する(in-flight は route 遅延で決定化。
  ガード削除ミューテーションで RED になることを確認)
- 実害のない劣化は「既知挙動」として報告を受け、固定するかを裁定する
  (少なくとも spec の挙動仕様に1行残す)
- 純表示系(非同期面なし)の機能ではこのフェーズをスキップしてよい

## Phase 3: PR

**PR は機能単位(1機能 = 1ブランチ = 1PR。「機能」= feature-map / `@feature-<name>`
タグの単位)。** 複数機能に触れていたら PR を分ける。

`pnpm check`(規約検証込み)→ `pnpm e2e:smoke` の順で通してから PR を作成。
CI がモックE2Eを実行し、サマリとメディア(録画・段階スクショ)をPRコメントに投稿する。

PR 作成後、完了報告の前に:

- CI が green になることを確認する(落ちたら証跡(録画・trace・スクショ)から
  診断する — ローカル再現より先に CI の一次データを読む)
- PRメディアコメントを自己レビューする(対象機能のメディアだけが載っているか、
  録画・スクショが仕様どおりの見た目か)
- UI の見た目を変えた PR は `gh workflow run update-snapshots.yml --ref <branch>` で
  VRT baseline を再生成する。**dispatch は常に1本ずつ**(並走 PR で同じ baseline を
  再生成すると binary conflict になる。ci-media 等の共有ブランチへの書き込みも同様)

## 依存する作業列は Stacked PR で積む(マージ待ちで直列化しない)

前の機能・修正がマージされないと次に進めない作業列は、マージを待たずに
Stacked PR(`gh stack init / add / submit`)でレイヤとして積む。各レイヤは
独立にレビュー・CI され、下のレイヤがマージされると上は自動 rebase/retarget
される。人間のマージ往復がサイクルタイムの支配項になるのを防ぐのが目的。

- **レイヤの単位も機能単位**(1レイヤ = 1機能 = 1PR)。スタックは機能を
  「積む」ためのもので、複数機能を1レイヤに「束ねる」理由にはならない。
  例外は同一機能内の「土台 → 適用」分割(各レイヤの検証が独立に閉じる場合。
  スタック全体で1機能)
- **VRT baseline の再生成は main を直接 target しているレイヤだけ**で行う。
  上位レイヤで regen すると、下位マージ時の自動 rebase で baseline PNG が
  binary conflict する(単一飛行原則のスタック版)。上位レイヤの見た目変更は
  自分が main 直 target に降りてきてから regen する
- 深いスタックは下位マージのたびに上位の CI が再実行される。e2e ~8分の
  現状では **3〜4 レイヤまで**を目安にする
