# dev-cycle: 実装とテストを並列で進める機能開発サイクル

「E2Eは最後にまとめて」を禁止し、**機能単位でE2Eまで完了させる**ためのワークフロー。

## Phase 0: 仕様化(メインセッションで行う)

`specs/<feature>.md` を作成する。含めるもの:

- ユーザーストーリーと受け入れ条件
- 公開インターフェース(APIエンドポイント、型、data-testid)— test-writer はこれだけを頼りにテストを書く
- **テスト層の割り当て**(docs/POLICY.md の判定表に従う):
  - ユニット観点: 純粋ロジック(パーサ、reducer等)
  - コンポーネント観点: 実ブラウザ挙動(逐次描画・スクロール等)→ Vitest Browser Mode。
    `page.clock`/`page.route`/video が必要なものだけ Playwright CT
  - E2E観点: 正常系1本 + 失敗系(最大2本)。失敗系は「UIに専用ハンドリングがある失敗」のみ

仕様が曖昧なままPhase 1に進まない。テスト観点を仕様に含めることが、後段の暴走(テストケース無限列挙)を防ぐ。

## Phase 1: 並列実行

Agent tool で **test-writer と implementer を同一メッセージで同時に起動**する(それぞれ `isolation: worktree` で隔離済み)。

- test-writer への指示: `specs/<feature>.md` を渡し、RED確認まで
- implementer への指示: `specs/<feature>.md` を渡し、実装(この時点ではテストなしで仕様から実装)

TDDを厳密にする場合(推奨・複雑な機能): test-writer を先に完了させ、失敗テストをコミットしてから implementer を起動する直列版に切り替える。単純な機能は並列版で速度を優先してよい。

## Phase 2: マージと検証

1. テスト → 実装 の順でメインブランチ(または機能ブランチ)にマージ
2. `npm run test:unit` — 全グリーンまで修正(TDDゲートを併用: `touch .claude/tdd-gate`)
3. `npm run e2e -- --grep @feature-<name>` — この機能のE2Eがグリーンになるまで修正
4. implementer がテスト側の問題を指摘していた場合はここで裁定し、必要ならテストを修正(修正はメインセッションが行う)

**この機能のモックE2Eがグリーンになるまで、機能は「完了」ではない。**

## Phase 2.5: 反証(敵対的レビュー)

グリーンになったら、**作業に関与していない新規コンテキスト**で adversarial-reviewer
サブエージェントを起動する(`isolation: worktree` なので破壊的検証も安全)。

- 入力: `specs/<feature>.md` と機能名。実装経緯・会話コンテキストは渡さない
- レビュアーは「テストを通したまま仕様を破るミューテーション」を実際に試み、
  成立した反証だけを再現手順つきで報告する(口頭指摘のみは却下してよい)
- **反証が成立した場合**: まず反例を新しいテストケースとして固定(RED確認)し、
  その後に修正する。反証をテスト資産に変換してからでないと修正に入らない
- **反証失敗(頑健)の場合**: そのまま Phase 3 へ。空振りは正常な結果
- レビュアーの報告が「correctness に影響し反例を再現できたもの」以外を含んでいたら、
  その項目は無視してよい(過剰報告はレビューの失敗であり、対応義務はない)

## Phase 3: PR

1. `npm run e2e:smoke` で他機能のスモークに回帰がないことを確認
2. PRを作成。CI(PRレーン)がモックE2Eを実行し、サマリをPRコメントに投稿する

## テストケース選定ルール(必読)

- 正常系: 機能につき1本。ユーザーストーリーの主経路のみ
- 失敗系: 最大2本。**UIに専用のハンドリングが実装されている失敗のみ**(エラーバナー、リトライ、タイムアウト表示)。モック層で決定的に再現できるものに限る
- 3本目の失敗系が欲しくなったら機能分割のサイン
- 例外: Phase 2.5 の反証フェーズで成立した反例の固定テストは上限に数えない
  (仕様の受け入れ条件が無防備だった証拠なので、必ず追加する)
- LLM出力の品質・妥当性はE2Eで検証しない(evalsレーンの守備範囲)
- 実LLMを呼ぶテストは `@backend` タグを付け、構造的アサーション(空でない・エラーでない・完了した)のみにする

## タグ規約

| タグ | 意味 | 実行タイミング |
|---|---|---|
| `@feature-<name>` | 機能単位の識別 | 当該機能の変更時 |
| `@smoke` | 主経路 | 全PR |
| `@backend` | 実バックエンド結合(将来: 実LLM) | nightly |
| `@quarantine` | flaky隔離中 | nightlyのみ・ゲート外 |
