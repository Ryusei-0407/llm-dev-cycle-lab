# dev-cycle: 実装とテストを並列で進める機能開発サイクル

「E2Eは最後にまとめて」を禁止し、機能単位でE2Eまで完了させる。
テスト層の判定表と共通規約は docs/POLICY.md(このスキルでは繰り返さない)。

## Phase 0: 仕様化(メインセッション)

`specs/<feature>.md` を書く: ユーザーストーリー、受け入れ条件、公開インターフェース
(APIエンドポイント、型、data-testid)、テスト観点の層割り当て。

test-writer は仕様**だけ**からテストを書くので、仕様には検証に必要な具体物
(ワイヤフォーマット、実データ例、モックの型)を含める。散文より具体物が効く。
仕様が曖昧なまま先へ進まない — テスト観点を仕様に含めることが後段の暴走を防ぐ。

## Phase 1: 並列実行

test-writer と implementer を**同一メッセージで同時に起動**する(各自 worktree 隔離)。
どちらにも `specs/<feature>.md` を渡す。

厳密なTDDが必要な複雑な機能では直列版に切り替える:
test-writer を先に完了させ、失敗テストをコミットしてから implementer を起動する。

## Phase 2: マージと検証

テスト → 実装の順にマージし、ユニット → その機能のE2E の順でグリーンにする
(TDDゲート併用: `touch .claude/tdd-gate`)。
implementer がテスト側の問題を指摘していた場合はここでメインセッションが裁定する。

**この機能のモックE2Eがグリーンになるまで、機能は「完了」ではない。**

## Phase 2.5: 反証(敵対的レビュー)

adversarial-reviewer を新規コンテキストで起動する。渡すのは仕様と機能名のみ
(実装経緯・会話コンテキストは渡さない)。

- 反証が成立したら: **反例をテストとして固定(そのテストがミューテーションを殺すことを確認)
  してから**修正に入る。反証はテスト資産に変換する
- 反証失敗(頑健)なら: そのまま Phase 3 へ。空振りは正常な結果
- 再現手順のない指摘・correctness に関係ない指摘は対応不要(過剰報告はレビュー側の失敗)

## Phase 3: PR

`pnpm e2e:smoke` で回帰がないことを確認して PR を作成。
CI がモックE2Eを実行し、サマリとメディア(録画・段階スクショ)をPRコメントに投稿する。
