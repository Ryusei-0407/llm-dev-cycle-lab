# Feature: ticket-model — チケットデータモデル拡張

Linear ライク刷新(フェーズ1)。チケットに番号・担当者・ラベル・更新時刻・
アクティビティ履歴を追加し、一覧のカーソルページネーションを用意する。
UI への露出は最小限(一覧行と詳細への表示・操作)にとどめ、本格的な画面刷新は
フェーズ2以降が行う。

## ユーザーストーリー

- エージェントとして、チケットを `SUP-12` のような短い番号で参照したい
- エージェントとして、チケットに担当者を割り当てて誰が対応中か分かるようにしたい
- エージェントとして、チケットにラベル(auth / billing など)を付けて分類したい
- エージェント・顧客として、チケットの状態変更・割り当ての履歴をスレッド内で確認したい
- (フェーズ2の準備)一覧をページ単位で取得できる API が欲しい

## Model(ワイヤ形式)

```ts
type Label = { name: string; color: string }; // color は "#rrggbb"

type Ticket = {
  id: string; // uuidv7(既存)
  number: number; // 1始まりの連番。表示は `SUP-${number}`(表示責務は web)
  subject: string;
  status: "open" | "in_progress" | "resolved";
  priority: "low" | "medium" | "high";
  requesterEmail: string;
  assigneeEmail: string | null; // 未割り当ては null
  labels: Label[]; // name 昇順で返す(決定的)
  createdAt: string; // ISO
  updatedAt: string; // ISO
};

type TicketEvent = {
  id: string; // uuidv7
  type: "status_changed" | "assignee_changed" | "labels_changed";
  actorEmail: string; // 操作したユーザ
  payload:
    | { from: Ticket["status"]; to: Ticket["status"] } // status_changed
    | { from: string | null; to: string | null } // assignee_changed(email)
    | { from: string[]; to: string[] }; // labels_changed(ラベル name 昇順)
  createdAt: string; // ISO
};
```

既存の `Ticket` 利用箇所(一覧・ボード・詳細・story・E2E スタブ)は追加フィールド分を
更新する。`tickets.list` の返却形は `Ticket[]` のまま(フィールド追加のみ、後方互換)。

## DB(apps/api/db/schema.sql / seed.sql)

```sql
-- tickets に追加するカラム
number bigint GENERATED BY DEFAULT AS IDENTITY UNIQUE NOT NULL,
assignee_email text,                                   -- NULL = 未割り当て
updated_at timestamptz NOT NULL DEFAULT now()

-- ラベルカタログ(色は UI 変更なしで済むようサーバ側が持つ)
CREATE TABLE labels (
  id uuid PRIMARY KEY DEFAULT uuidv7(),
  name text NOT NULL UNIQUE CHECK (char_length(name) BETWEEN 1 AND 32),
  color text NOT NULL CHECK (color ~ '^#[0-9a-f]{6}$')
);
CREATE TABLE ticket_labels (
  ticket_id uuid NOT NULL REFERENCES tickets(id) ON DELETE CASCADE,
  label_id uuid NOT NULL REFERENCES labels(id) ON DELETE CASCADE,
  PRIMARY KEY (ticket_id, label_id)
);

-- アクティビティ履歴。payload はワイヤ形式の payload と同一の JSON
CREATE TABLE ticket_events (
  id uuid PRIMARY KEY DEFAULT uuidv7(),
  ticket_id uuid NOT NULL REFERENCES tickets(id) ON DELETE CASCADE,
  actor_email text NOT NULL,
  type text NOT NULL CHECK (type IN ('status_changed', 'assignee_changed', 'labels_changed')),
  payload jsonb NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now()
);
```

シード(既存3チケットへの追加。番号は INSERT 順で 1, 2, 3 になる):

```sql
-- labels カタログ(固定5種)
INSERT INTO labels (id, name, color) VALUES
  ('00000000-0000-7000-8000-000000000201', 'auth',    '#e2626b'),
  ('00000000-0000-7000-8000-000000000202', 'billing', '#f2c94c'),
  ('00000000-0000-7000-8000-000000000203', 'api',     '#6a8dff'),
  ('00000000-0000-7000-8000-000000000204', 'email',   '#27a644'),
  ('00000000-0000-7000-8000-000000000205', 'request', '#9a6ae2');

-- 付与: "Cannot login to dashboard"→auth / "Billing question"→billing /
--        "Feature request: dark mode"→request
INSERT INTO ticket_labels (ticket_id, label_id) VALUES
  ('00000000-0000-7000-8000-000000000001', '00000000-0000-7000-8000-000000000201'),
  ('00000000-0000-7000-8000-000000000002', '00000000-0000-7000-8000-000000000202'),
  ('00000000-0000-7000-8000-000000000003', '00000000-0000-7000-8000-000000000205');

-- 担当者: "Billing question" のみ agent@example.com、他は未割り当て
UPDATE tickets SET assignee_email = 'agent@example.com'
  WHERE id = '00000000-0000-7000-8000-000000000002';
```

- 既存シードの `updated_at` は明示指定しない(DEFAULT now())。テストは
  updated_at の**値**ではなく「操作で単調増加すること」だけをアンカーにする
- `number` は `GENERATED BY DEFAULT AS IDENTITY`: シードは明示せず挿入順で 1..3、
  新規作成は 4 以降。値の再利用・欠番は仕様として許容(UNIQUE のみ保証)

## サーバー(oRPC。認可の既定は specs/authz.md: 全手続きセッション必須)

### 変更

- `tickets.list` — 返却 `Ticket[]`(新フィールド込み)。並びは従来どおり
  created_at DESC, id DESC。ロールスコープも従来どおり
- `tickets.get` — 返却が `{ ticket, messages, events }` になる。
  `events: TicketEvent[]` は created_at ASC, id ASC
- `tickets.reply` — 成功時に該当チケットの `updated_at` を now() に更新する
  (イベントは記録しない。履歴対象は下記3種のみ)
- `tickets.setStatus` — 変更成功時に `status_changed` イベントを記録し
  `updated_at` を更新。**同値への変更(open→open)はイベントを記録しない**
  (updated_at も更新しない。返却は現行チケットのまま成功)

### 新規

- `tickets.setAssignee` input `{ id: string, assigneeEmail: string | null }` → `Ticket`
  - agent 専用(customer は FORBIDDEN)。存在しない id は NOT_FOUND
  - `assigneeEmail` は users に存在する **role='agent'** のメールのみ許可。
    それ以外(customer のメール・未知のメール)は `ORPCError("BAD_REQUEST",
{ message: "not an agent" })`。`null` で未割り当てに戻す
  - 変更成功時 `assignee_changed` イベント + updated_at 更新 + `ticket.updated`
    ブロードキャスト。同値(null→null 含む)はイベント・更新・配信なしで成功
- `tickets.setLabels` input `{ id: string, labels: string[] }` → `Ticket`
  - agent 専用。ラベル **name** の配列で全置換(空配列=全解除)。重複 name は
    1つに正規化。カタログにない name は `ORPCError("BAD_REQUEST",
{ message: "unknown label" })`
  - 変更成功時 `labels_changed` イベント(payload from/to は name 昇順)+
    updated_at 更新 + `ticket.updated` ブロードキャスト。集合として同値なら何もしない
- `tickets.labels` input なし → `Label[]`(name 昇順)。セッション必須(ロール不問)
- `tickets.agents` input なし → `{ email: string; name: string }[]`(email 昇順)。
  agent 専用(担当者セレクトの選択肢用)
- `tickets.listPage` input `{ cursor?: string, limit?: number }` →
  `{ items: Ticket[], nextCursor: string | null }`
  - limit は int 1..100、省略時 50。並び・ロールスコープは list と同一
  - keyset ページネーション: `(created_at, id) < (カーソル位置)` の行を返す。
    OFFSET は使わない
  - `cursor` は不透明トークン: `base64url("${createdAt ISO}|${id}")`。
    デコード不能・形式不正は `ORPCError("BAD_REQUEST", { message: "invalid cursor" })`
  - 最終ページでは `nextCursor: null`。**残件がちょうど limit 件のときも**、次の
    ページ取得が空になるのではなく `nextCursor: null` を返すこと(先読み1件で判定)

### 整合性

- イベント記録と本体 UPDATE は**同一トランザクション**(片方だけ残らない)
- `updated_at` はサーバ側 `now()`(クライアント入力を信用しない)

## UI(最小露出)

### 一覧(/tickets)・各行

- `data-testid="ticket-number"` — `SUP-1` 形式で表示
- `data-testid="ticket-labels"` 内に各 `data-testid="ticket-label"` — name を表示、
  色は `style` の background などに `color` を反映(見た目の詳細は自由)
- `data-testid="ticket-assignee"` — 担当者の name(users 由来ではなく
  `assigneeEmail` の @ 前でよい: `agent@example.com` → `agent`)。未割り当ては `–`

### 詳細(/tickets/$id)

- ヘッダに `data-testid="ticket-number"`(`SUP-1` 形式)
- スレッド内イベント行 `data-testid="ticket-event"`(created_at 順に messages と
  時系列マージして表示)。表示文言(完全一致でテスト可能に固定):
  - status_changed: `状態: {from} → {to}`(値は open/in_progress/resolved の生値)
  - assignee_changed: `担当者: {from ?? "未割り当て"} → {to ?? "未割り当て"}`(email 生値)
  - labels_changed: `ラベル: {to を ", " 結合}`(空は `ラベル: なし`)
- 担当者セレクト `data-testid="assignee-select"`(**agent のみ表示**)。
  選択肢: `未割り当て`(値 "")+ `tickets.agents` の name。変更で setAssignee
- ラベル編集(**agent のみ表示**): カタログ全ラベルを
  `data-testid="label-toggle-{name}"` のトグルで表示、クリックで付け外し
  (現在の付与状態を反映)。変更ごとに setLabels で全置換を送る
- customer にはセレクト・トグルを出さない(番号・ラベル・イベントの閲覧は可)

### リアルタイム

- `ticket.updated` 受信時の invalidate は既存機構のまま(assignee/labels 変更も
  同イベントなので追加実装なし)

## E2E観点(@feature-ticket-model、実バックエンド)

1. 正常(@smoke): agent でログイン → /tickets で "Billing question" 行に
   `SUP-2`・`billing` ラベル・担当者 `agent` が見える → 詳細へ → assignee-select で
   `未割り当て` に変更 → イベント行
   `担当者: agent@example.com → 未割り当て` が現れる → `label-toggle-api` を
   クリック → ticket-labels に `api` が現れ、イベント行 `ラベル: api, billing` が
   現れる。最終状態に aria snapshot
2. 状態変更の履歴: 詳細(または一覧の既存セレクト)で status を変更 →
   詳細のイベント行 `状態: in_progress → resolved` 表示(シード
   "Billing question" 以外の、他テストと競合しないチケットを新規作成して使う)
3. 認可: customer でログイン → 自分のチケット詳細に assignee-select と
   label-toggle が**存在しない**(イベント行・番号は見える)

listPage は UI が未接続のためE2E対象外(unit で網羅)。共有DBアンカー規約
(件数アサーション禁止・シード変更禁止)は POLICY.md に従う。

## component観点(Vitest Browser Mode)

- ticket-list 行: number/labels/assignee の描画(未割り当て `–`、ラベル0件、
  複数ラベルの各状態)
- 詳細のイベント行: 3種 type の文言レンダリング(messages との時系列マージ含む)

## unit観点

- store:
  - list/get が number・assigneeEmail・labels(name 昇順)・updatedAt を返す
  - create で number が既存最大より増える(具体値は 4 に依存しない)
  - setAssignee: agent 検証(customer/未知 → エラー)、null 解除、イベント記録、
    updated_at 更新、同値スキップ
  - setLabels: 全置換・空配列・未知 name エラー・重複正規化・イベント payload
    (from/to 昇順)・同値スキップ
  - setStatus: 同値スキップ、イベント記録
  - reply 後に updated_at が増加
  - イベントとチケット更新の原子性(トランザクション)
  - listPage: 先頭ページ・2ページ目(カーソル追従)・最終ページ nextCursor null・
    残件ちょうど limit 件で null・created_at 同値タイの id タイブレーク・
    不正カーソル BAD_REQUEST・limit 範囲外は zod でエラー・ロールスコープ
- schema(zod): setAssignee / setLabels / listPage の入力検証
- cursor codec: encode→decode 往復、不正入力
